# Contributing to sentinel

Thanks for helping. This guide covers the workflow; the design lives in
[docs/PLAN.md](docs/PLAN.md) and the [ADRs](docs/adr).

## Setup

```sh
npm ci
npm run check      # lint + format check + typecheck + unit tests
npm run build      # bundle to dist/ with tsup
npm run test:e2e   # runs the built CLI; build first
```

Node.js ≥ 22 and git are required; `gh` is needed for anything that touches pull requests.

## Branches and pull requests

- Branch from `main`; never push to it. Use a short, typed name such as `feat/…`, `fix/…` or
  `docs/…`.
- One logical change per PR. Describe what changed and why, and note any deviation from the plan.
- CI must be green on Ubuntu, macOS and Windows (Node 22 and 24), plus lint, format, typecheck and
  CodeQL. The coverage gate is 85% lines.
- A human merges. Do not merge your own PR without review where review is available.

## Changesets

Every user-facing change needs a changeset: run `npm run changeset`, pick the bump and describe the
change, and commit the generated file with the PR. Docs-only and test-only changes need none.
On merge to `main` the Release workflow opens a "chore: version packages" PR; merging it tags
`vX.Y.Z` and creates a GitHub Release. Nothing is published to npm
([ADR-0006](docs/adr/0006-marketplace-distribution.md)).

## Code, tests and lint

- TypeScript, strict. ESLint uses `strictTypeChecked`; Prettier (print width 100) is enforced by
  `npm run format:check`. `npm run format` fixes formatting.
- sentinel never calls an LLM ([ADR-0002](docs/adr/0002-no-llm-calls.md)). Rules belong in
  deterministic code and tests, not in prompt text alone.
- Core logic takes its file system, process runner and clock as injectable dependencies so tests
  need no real GitHub. Unit tests live in `test/unit`; `test/e2e` runs the built CLI.
- Exit codes are part of the contract: see the table in the [README](README.md#exit-codes).

## The plugin and its bundle

The repository is the plugin marketplace. `plugins/sentinel/skills/*` holds the skills, and each
skill folder carries a copy of the CLI as `scripts/sentinel.mjs`. Marketplaces install by cloning
git without a build step, so the bundle is committed. Rules
([ADR-0006](docs/adr/0006-marketplace-distribution.md)):

- **Feature PRs do not edit the bundle.** It is regenerated by the changesets version PR
  (`version-packages` runs `npm run build:plugin`), so `main` always carries the bundle of the
  last release and feature PRs carry no generated diffs.
- **The one exception:** a PR whose skill names a CLI command that is not in the committed bundle
  must rebuild the bundle (`npm run build:plugin`) in the same PR. The skill lint test runs every
  command a skill names against the committed bundle and fails otherwise.
- **Hand-written vs generated.** `.claude-plugin/marketplace.json` and
  `plugins/sentinel/.claude-plugin/plugin.json` are written by hand. The Codex, Cursor and Agent
  Plugins manifests and `schema/config.json` are generated; do not edit them.
- **`npm run check:plugin`** checks that the committed plugin is internally consistent: derived
  manifests match, versions agree, every bundle copy is identical and runs. It never compares
  against `src/`, so feature work cannot fail it. Release CI additionally rebuilds the bundle and
  fails if it differs from the committed one before a tag is created.

If your merge conflicts in a generated file, resolve it by running `npm run build:plugin` again.

## Core PRs and skill PRs

Split work by whether it touches the bundle ([sequencing in the plan](docs/PLAN.md)):

- **Core PRs** (code and tests, no skill) never touch the bundle, so several can be open and merge
  in any order.
- **Skill PRs** add or change a `SKILL.md` and rebuild the bundle, so they merge one at a time.
  A skill ships in the same milestone as the CLI command it calls.

## Skills

A skill is a folder with `SKILL.md`: the `name` equals the folder name (lowercase, hyphenated) and
`description` is at most 1024 characters. Skills invoke the CLI by a path relative to their own
folder (`node scripts/sentinel.mjs <command>`), repeat every guardrail, and reach the issue tracker
only through `sentinel issue resolve`; they must not hard-code `gh issue`, `glab issue` or tracker
REST calls. The lint tests in `test/unit/skills.test.ts` enforce this.
